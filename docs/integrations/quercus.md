# Quercus knowledge synchronization

Quercus is a trusted backend Canvas integration fixed to `https://q.utoronto.ca`. The personal token is stored only in Windows Credential Manager under the `quercus` namespace and is validated with the current-user profile endpoint. Canvas identifiers are treated as opaque strings. Replacing a token for the same identity preserves selections; a different identity cannot be connected while any local course copy remains.

Course selection defaults to none. Settings lists accessible active, invited/pending, and completed courses. Saving the exact selected set queues one coalesced background sync. Deselected courses stop receiving updates but remain readable. The square delete action is available for tracked and untracked courses. It permanently removes any course directory and synchronization records while holding the synchronization lock, then stores an account-scoped exclusion so the deleted course no longer appears in later Canvas course listings.

Selected courses are mirrored under `runtime/act/knowledge/quercus/<course>/` as readable Markdown and downloaded files. Original files use `files/raw/<canvas-folder-tree>/`; optional derived Markdown uses the symmetrical `files/processed/<canvas-folder-tree>/`. The mirror includes course overview/syllabus, ordered modules, assignments and the current user's available submission/grade feedback, pages, announcements, classic and New Quiz material visible to that user, aggregate grades, and accessible Canvas files. Canvas authorization and availability locks remain authoritative. Quercus content is untrusted data and is not injected into Act context.

Stable sanitized title paths are stored in SQLite alongside Canvas identity, parentage, version/update fields, fingerprints, size/type, download state, and sync generations. The knowledge tree contains no synchronization manifests, frontmatter, sidecars, or ID-bearing names. HTML removes active content, event handlers, unsafe URL schemes, and form content.

Each run enumerates resource types independently and rewrites only changed content. A complete enumeration removes stale local resources; a partial or failed enumeration preserves them. Downloads stream to a temporary sibling and publish atomically. Files up to and including 8 GiB are eligible; larger or unknown-size files are recorded as skipped in SQLite without a local placeholder. Redirects must remain public HTTPS destinations, and bearer credentials are removed before following cross-origin file redirects.

When Canvas forbids the course-wide files listing, the sync falls back to file IDs exposed through the accessible syllabus, Modules, Assignments, Pages, and Announcements. It requests metadata and downloads each referenced file independently, honors link verifiers only on canonical Quercus metadata requests, records inaccessible references as skipped, and continues after individual failures. Because this is not a complete course-file enumeration, it never deletes older mirrored files that are absent from the discovered references.

The fixed `backend.quercus.knowledge.sync` platform service runs daily at 10:00 `America/Toronto` with durable at-most-once occurrence claims and latest-missed startup catch-up. Failed occurrences are not retried, only one Quercus sync may run at a time, and individual course/resource failures produce partial results without stopping unrelated work. This service is not a generated skill, Eidolon function, or MCP tool.

## Optional file processing

File processing is global and defaults to `none`. Settings may enable `marker_surya_llamacpp`, which immediately queues one coalesced backfill across selected and retained courses; later syncs process new or changed downloads. Disabling processing retains existing derived Markdown but managed Act instructions tell the agent to ignore it. With processing enabled, Act checks `files/processed/` first and consults the corresponding original in `files/raw/` only when Markdown is absent, reports failure, or lacks enough information.

The trusted backend resolves `marker_single` from its own PATH and runs it directly without a shell, one file at a time, with `--mode balanced`, Markdown output, image extraction disabled, and a 60-minute timeout. The user selects an absolute llama.cpp installation directory containing `llama-server.exe`. At the start of a pass, the backend uses Marker’s Python environment to start one keep-alive Surya llama.cpp server, validates its loopback endpoint and recorded PID, and passes that endpoint to every Marker conversion through `SURYA_INFERENCE_URL`. The same server is reused for the full processing or synchronization pass and is terminated by exact process tree without a Windows console-control broadcast when the pass or backend shuts down. Marker never owns per-file server teardown, and a separately started endpoint is not required. PDF, common image, PPTX, DOCX, XLSX, HTML, and EPUB inputs are eligible; non-PDF support requires the user-installed `marker-pdf[full]` dependencies. Eidolon does not install or update Marker or llama.cpp.

The processing dispatcher is owned by the backend lifecycle. Shutdown stops the active Marker process tree and the pass-owned inference server with bounded waits, marks interrupted work pending for the next startup, and removes stale Marker and llama-bootstrap temporary directories after each pass and when startup resumes. Startup also cleans remnants from the former Act-workspace location. Course counts are committed after each file. Structured backend logs include backend/parent PIDs, worker/thread lifecycle, course and resource identifiers, Marker, inference-bootstrap, and llama-server PIDs, ownership, durations, return codes, bounded failure log tails, interruption reason, and shutdown completion; access tokens and Canvas download URLs are never logged.

Temporary Marker and llama-bootstrap output stays under the backend-owned `runtime/backend/quercus-processing/` directory, which is removed when empty; only one validated nonempty UTF-8 Markdown file is atomically published. Missing prerequisites, unsupported types, timeouts, invalid output, and failed processes create the exact placeholder `Processing failed, refer to the raw file.` Ordinary sync, backfill, and startup recovery do not retry an unchanged failed file. Interrupted files remain pending and resume automatically; changed source files are processed as new work. The explicit **Reprocess failed files** Settings action moves current failures back to pending and queues one coalesced pass. Processing fingerprints, paths, status, errors, and counts stay in SQLite. Canvas sync and processing status remain independent.
