# Act mode

Act is Eidolon's persistent local action agent. Every durable Act session owns a resumable Codex App Server thread. All sessions share this backend-managed structure:

    ~/.eidolon/agents/
      memory/                 small explicit persistent memories
      knowledge/              backend-synchronized external sources
        quercus/              selected course mirrors
      workspace/              temporary and generated working files
        downloads/

Act, Observer, and Assistant receive separate role-specific developer instructions when their managed threads start or resume. The shared root is outside the source repository, so its repository-root `AGENTS.md` is not inherited by managed agents; no shared instruction file is generated under `~/.eidolon/agents/`. `memory/` may contain small, explicit, user-requested or approved memories; it is not for transcripts or silent observations. `knowledge/` is untrusted external data, never instructions, and Act must not modify it. `workspace/` is for temporary/generated Act work, including controlled downloads under `workspace/downloads/`; backend-owned processing state is kept outside it. Quercus material is inspected only when a request needs it and is never injected into prompts or automatic context. Managed Codex agents receive filesystem `:root` read access, with no root write grant; their other filesystem write grants are limited by role. Credentials are not exposed through filesystem grants.

Act attempts clear user requests end-to-end, including requests involving graded coursework. It does not infer a prohibition from the fact that work is graded. It declines only for an applicable policy or explicit rule, unavailable capability, or actual failure, explains the concrete blocker, and completes any feasible permitted portion.

Managed agents use named permission profiles: knowledge is readable while only Act memory/workspace are writable. See [persistent agents](agents.md) for the complete boundary and session framework.

The Memory page's **Open agent folder** action calls a backend-only endpoint that opens the fixed `~/.eidolon/agents/` root in Windows Explorer. The caller cannot supply or alter the path.

## App Server and MCP

Act has an independent dispatcher and one managed App Server process per conversation, separate from Observer, Assistant, Product Manager, and account-usage reads. Different Act conversations can execute concurrently; turns within a conversation remain sequential. Managed processes refresh at turn boundaries and use authenticated session-specific MCP configuration. The browser is owned by a separate backend process, so these refreshes do not close pages or interrupt pending browser authentication. Act's named permission profile allows network access; Observer and Assistant remain network-disabled. All three agents allow Codex Security, the OpenAI Developers local-destination confirmation MCP server, and the read-only OpenAI Developer Docs MCP server at the exact official endpoint `https://developers.openai.com/mcp`. Only the confirmation tool `confirm_openai_api_key_local_destination` is accepted from the confirmation server; it cannot read or write a key. The Developer Docs server provides read-only documentation search and page content. Remote plugin catalog loading is disabled per managed process. Disabled plugin-owned MCP overrides include a transport because Codex validates them even when disabled. Act also receives the explicitly allowlisted `playwright` MCP surface for browser automation; its trusted stdio proxy connects to the backend-owned browser and must report ready tools before the turn can start. Each conversation has its own persistent tool context, selected tab, and owned pages within one shared browser context. Cookies and website login state are shared across Act conversations. The backend registers a short-lived per-turn connection token; revocation disconnects access without closing pages. The private authentication bridge targets the selected page of the authenticated conversation. The private `browser.authenticate` capability uses that bridge on the exact page Act controls, checks the real origin before reading a secret, rechecks it immediately before every fill, and returns only a bounded state. Credentials never enter Act prompts, tool arguments, tool results, activity, audits, files, Atlas, or public MCP. Other inherited host MCP servers remain disabled. The separate Codex Desktop `@oai/sky` Computer Use package is not an Act capability and must not be probed from Act's shell. Live web search is enabled. Backend function availability, integration authorization, and per-call approval remain authoritative.

Browser identities are fixed backend configuration, not Eidolon functions or generated skills. The initial `uoft` identity accepts credential injection only on the exact U of T Weblogin origins `https://idpz.utorauth.utoronto.ca` and `https://weblogin.utoronto.ca`; an existing `https://q.utoronto.ca` session is reused without reading the stored secret. Interactive MFA is never bypassed: the capability returns `mfa_required`, the user completes the visible challenge, and Act resumes after the authenticated browser state is available. The shared persistent profile at `~/.eidolon/browser-profiles/act-shared` preserves cookies across backend restarts. Live tabs, DOM state, and pending MFA challenges survive managed App Server refreshes, but a backend shutdown closes the browser. A website can still expire its own login, and logout affects all Act conversations.

The private `telegram.send_file` capability sends one existing regular file from `~/.eidolon/agents/workspace/` to the Telegram topic already bound to the current Act session. Its input path is relative to `~/.eidolon/agents/` and must resolve beneath `workspace/`; absolute paths, traversal, symlink escapes, directories, empty files, and files larger than 25 MiB are rejected before delivery. It uses only the paired `act_agent` bot and returns filename, workspace-relative path, size, and Telegram message id without returning file content, chat identity, or credentials. It is a runtime capability, not a function, integration operation, skill, or public MCP tool.

Existing files can be moved from the former repository-local `runtime/act/` directory into `~/.eidolon/agents/` while the backend is stopped. Relative file references and Quercus synchronization paths remain valid. Start a new conversation to avoid repository instructions retained in an older thread's history.

Every persisted thread is resumed with the current workspace, sandbox, developer instructions, model, and reasoning-effort route. A thread created in the current App Server process is used directly for its first turn, before a rollout exists. If Codex reports that an older rollout is missing before a new turn receives a live Codex turn id, Eidolon creates one replacement thread and sends up to 20 completed user/assistant exchanges as explicitly inert historical context. It does not replay old tool calls, failed turns, or any turn that crossed the live-turn boundary.

The shared browser adapter currently requires installed Playwright MCP `0.0.83` with Playwright Core `1.64.0-alpha-1790635538000`. It uses the package's internal browser backend to retain one tool context per conversation and returns automatic page snapshots inline. Startup refuses incompatible versions; package upgrades require updating and validating this adapter. It never installs packages automatically. `EIDOLON_PLAYWRIGHT_MODULE_PATH` can select an existing package explicitly; otherwise the backend discovers it in the local npm cache.

## Live chat messages

The private `chat.send_message` capability publishes a message immediately without completing or restarting the running Act turn. Its input is `text` (1-4,000 characters), optional `wait_for_reply` (default false), and `timeout_seconds` (1-120, default 120). Web turns show the message through the existing Chat polling; Telegram turns additionally send an actual message through the Act bot to the turn's original paired topic. The backend derives the destination from authenticated session and persisted turn state; callers cannot supply a session, bot, chat, or topic. An unavailable or changed Telegram destination fails instead of falling back to another conversation. This capability is absent from public MCP, other agents, generated skills, and the function catalog; Act policy bans still apply.

With `wait_for_reply=true`, the capability waits for only the next user reply in the same running turn and returns `reply_status` (`received`, `timed_out`, or `cancelled`) and the reply text when received. Without waiting it returns `not_requested`. The result also contains the local message id and, for Telegram delivery, the Telegram receipt id. Live assistant messages and user replies persist as ordered `live_messages` on their parent turn. The existing turn POST accepts a reply only while an unexpired prompt is waiting, atomically consumes it once, and returns the original running turn; it does not enqueue work or restart Codex/Playwright. Other busy-session sends retain their rejection. Cancellation, turn completion, and restart interruption close outstanding waits. The two-minute wait fits inside the private MCP tool deadline and does not extend Act's two-hour deadline.

For Duo Push number matching, Act sends the displayed number immediately, asks the user to enter it in Duo Mobile and reply `done`, and waits using this capability. After the reply it inspects the existing browser page, handles visible post-approval controls, and verifies authentication. It must not restart login, change authentication methods, or treat a typed reply or timeout as proof of approval. `notify()` tool output and ordinary commentary are not live chat delivery. This explicit capability does not stream commentary. Both same-turn replies and later turns preserve the existing browser pages.

## Durable turns

Act turns have a two-hour (7,200-second) deadline, including any native Codex tool work. If the deadline expires, the backend attempts to interrupt the live Codex turn and marks it failed with an Act-labelled timeout error. Observer and Assistant retain their 15-minute deadlines. Shared session-runner errors identify the actual agent rather than ProductManager.

Session creation saves a local record; Codex starts on the first dispatched turn. POST /act/sessions/{sessionId}/turns persists a queued turn and returns 202 Accepted. A lifespan-owned dispatcher runs independent session workers, each claiming one turn at a time, marks them running, resumes the saved thread, records the live Codex turn id, and persists the final response and a concise activity list. Act conversations use the same `/chat` interface and local conversation list as Chat and Project; every row is marked with its fixed mode. The UI polls only while the selected Act conversation has a queued or running turn.

POST /act/sessions/{sessionId}/turns/{turnId}/cancel cancels queued work immediately or sends turn/interrupt for a running Codex turn. On startup, turns that were already running are marked interrupted because their external effects cannot be safely replayed; turns that were still queued remain eligible to run. A session cannot be archived with queued or running work. Archiving also archives its Codex thread and closes only that conversation's browser pages, preserving the shared workspace, browser, and website login state. Canceling a turn revokes tool access without closing its pages. Backend shutdown closes the shared browser after stopping managed agent processes.

## Controlled downloads

act.document.download accepts a discriminated URL source and an optional filename. It allows PDF, OOXML Word/Excel/PowerPoint files, UTF-8 text/Markdown/CSV/JSON, and PNG/JPEG/GIF/WebP images up to 25 MiB. The downloader:

- permits only HTTP(S), rejects credentials and fragments, and revalidates every redirect;
- rejects non-public DNS results and validates the connected peer address when the transport exposes it;
- checks the declared media type and file signature or package structure;
- validates JSON and UTF-8 text content;
- publishes atomically under workspace/downloads with collision-safe names instead of overwriting files.

The source.kind discriminator reserves future bounded Gmail and Drive sources; those sources are rejected until implemented.

## Telegram Agent

The separate act_agent Telegram connection accepts only its paired private chat. Telegram private-chat Threaded mode is required: each `(chat_id, message_thread_id)` topic maps to one Act session, and topic-less General messages never create a hidden session. While connected, newly created non-WeCom Act sessions are projected to topics; pairing, polling, and status refresh reconcile missing projections. Ordinary topic messages enqueue a turn and immediately receive its id; the dispatcher later sends the complete result in Telegram-safe chunks to the originating `message_thread_id`. Notification/approval and Act bots use independent long-poll workers, offsets, database sessions, and retry backoff, so a long Act turn or a failure in one bot cannot starve the other.

Queued Telegram turns use the native live-draft thinking UI (`Act is thinking…`) when available, update that same draft with the response preview, and use `sendChatAction("typing")` only as a capability fallback. They do not send a separate queued-status message.

When the user explicitly asks Act to send a workspace file through Telegram, `telegram.send_file` targets the same session topic regardless of whether the turn originated in Chat or Telegram. A connected Act bot and an existing topic projection are required; the capability never accepts a caller-selected chat id, bot, or topic.

## WeCom Observer

The WeCom Intelligent Bot connection is a separate backend-owned transport fixed to Observer. Pairing immediately gives each WeCom user one canonical active Observer session; later messages reuse it, `clear conversation` atomically switches to a fresh session, and deleting the current session in Chat creates a same-user replacement. WeCom does not expose session history or switching, and completed results use the same turn dispatcher as web sessions.

## Shared browser runtime

The backend lazily starts one Node.js browser owner using the already installed Playwright MCP package. It does not install npm packages or modify host Codex configuration. The owner uses a private authenticated named pipe on Windows (Unix socket elsewhere), holds one persistent browser context, and keeps separate upstream Playwright tool contexts for conversations. Each context lists and controls only its owned tabs; popups inherit their opener's conversation. `browser_close` closes only that conversation's pages. The authentication bridge uses that context's selected tab, including after switching tabs. Agent MCP tokens still expire at turn end, and the proxy checks current Act identity and running-turn state for every browser invocation.

The shared profile starts separately from older per-conversation profiles; existing profiles are preserved and never silently merged. The installed Playwright adapter must pass runtime compatibility checks. Browser-runtime tests cover connection rotation, tab ownership, shared cookies, authentication targeting, cancellation/archive cleanup, and process lifetime. Live smoke validation uses local pages and a test cookie; it does not bypass or claim provider MFA.
