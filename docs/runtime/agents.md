# Persistent agents

Act, Observer, and Assistant are built-in conversational agents backed by resumable Codex App Server threads. They are independent of generated function, service, and web-app skills and cannot be installed as skills. The Agents page exposes descriptions, effective policies, model/reasoning overrides, sessions, and Assistant proposals and assessments. Project planning remains separate.

## Workspace and authority

All three agents use `runtime/act/`. Role-specific developer instructions are supplied per thread; no shared managed instruction file is generated there. All agents receive `:root` read access; the native Windows elevated sandbox requires it when Codex loads `AGENTS.md`. They also receive read access to the managed `runtime/act/` root. Act can write workspace files and explicit, user-approved memory; Observer and Assistant have no filesystem write grants. The backend owns synchronized knowledge and `knowledge/assistant/plans/`.

Named Codex permission profiles grant `:root` read, minimal reads, and the managed runtime root to all three agents, plus only Act's memory/workspace write roots. Command networking is disabled except for Act. The backend disables inherited MCP servers except for Codex Security, the OpenAI Developers local-destination confirmation tool, and the read-only OpenAI Developer Docs MCP server at `https://developers.openai.com/mcp`, which are available to all agents; Playwright is available only to Act. The local-destination confirmation exception permits only `confirm_openai_api_key_local_destination`; the backend rejects any additional tools on that MCP server. This confirmation tool asks for a workspace-local env-file destination and cannot read or write a key. The Developer Docs server is restricted to the exact official endpoint and provides read-only documentation search and page content. Remote plugin catalog loading is disabled per managed process because a stale Cloudflare plugin entry fails configuration loading before named-server disables apply. Other plugins, apps, and delegation features remain disabled for every managed agent process. Codex Security and the local-destination confirmation server are temporary allowlist exceptions while Codex ignores per-process plugin disable overrides. An unsupported permission profile fails the turn instead of falling back to a broader sandbox. Filesystem read, filesystem write, network, and tool availability are separate controls. These are local single-user boundaries, not protection against a privileged host user or compromised backend.

Each agent has a default semantic read-only filter, maximum risk, explicit allowed function IDs, and explicit banned IDs. Bans win; explicit allows override the default semantic filter and risk limit. Integration read-only decisions use canonical registry effects, never MCP presentation hints. Ordinary catalog operations retain their availability, integration authorization, generated-function runtime permission, and per-invocation approval rules. Observer and Assistant default to read-only operations at any risk; generated functions remain write-capable by default. The backend writes assessment reports from validated structured results. Act permits all available agent-callable functions. Observer has no web search; Act and Assistant have live Codex search. Filesystem and search permissions are fixed per role in this milestone; editable function overrides do not change them.

## Authenticated MCP and durable turns

The public host MCP registration remains separate. Managed threads start with a required private STDIO MCP registration and an opaque credential bound to the agent and Eidolon session. Only credential hashes are stored in the application database. The credential is passed to the trusted MCP child, not ordinary shell processes or readable workspace files. Discovery filters the catalog and every invocation rechecks current identity and policy. Audit records include agent/session identity and the active turn when established, without arguments or credentials. Deferred function approvals retain agent attribution and recheck current policy at dispatch.

Sessions are saved before Codex starts; their first queued turn creates the Codex thread. One dispatcher per agent serializes its turns while unrelated agents remain independent. Telegram and WeCom are transport-only adapters over this same session infrastructure: Telegram resolves `(chat_id, message_thread_id)` and WeCom resolves one persisted current session per user. A connected conversational Telegram bot projects every newly committed active non-WeCom session for its agent to an idempotent topic mapping; pairing, polling, and status refresh backfill or retry missing projections. Each paired WeCom user always has one active current Observer session: pairing creates it, clear swaps it, and archiving it through Chat atomically replaces it for the same user. Turn rows snapshot the delivery provider, connection, chat/user, and Telegram thread so channel changes cannot redirect replies. Model routing is also independent: Act uses `act`, Observer uses `observer`, and Assistant uses `assessment` in the persisted Codex routing settings. The native Codex App Server thread name is the canonical generated title for all three agents: successful turns project a changed non-empty name to the session and existing Telegram topic, and Telegram manual renames update the native thread name. The shared title-sync service compares normalized values and keeps Telegram transport failures separate from turn success. Managed App Server processes restart at turn boundaries to refresh tool discovery and configuration, while saved Codex threads retain conversation context. Act alone receives the private `browser.authenticate` and `telegram.send_file` runtime tools, while Playwright remains an Act-only inherited host tool. These invocation surfaces are absent from Observer, Assistant, public MCP, the function catalog, and generated skills. Credentials are revoked after turns, archiving, and retention. Existing Act session/thread IDs are preserved, and the `/act` API remains an Act-only surface. Cancellation, archive, restart interruption, and missing-rollout recovery retain Act's existing behavior.

## Assistant assessments, proposals, and follow-ups

Each assessment starts a new Assistant session and uses its existing Telegram topic. The dispatcher selects the strict `AssistantAssessmentResult` native Codex App Server `outputSchema` only for the first turn when the backend-owned session origin is `assessment`. Every later turn uses the normal `{ response: string }` schema, including replies to Goal questions and ordinary follow-up conversation. Prompt wording does not select the schema. The Assistant instruction lives in `backend/app/agent_instructions/assistant.txt`; the backend renders both a deterministic function catalog with IDs, descriptions, and input schemas and a separate descriptive Act capability catalog. Neither catalog grants Assistant execution authority.

The assessment result contains ordered Todo Doer proposals, Goal Doer questions and proposals, and Opportunity Scout opportunities with optional proposals. The backend validates it once, writes the ordered opportunity title/description pairs to the existing Notion `Opportunities` report without approval, and persists proposals with action, provenance, fingerprint, status, Telegram metadata, and execution state. An empty opportunity list still produces a report. The former assessment-time plan and report MCP tools are unavailable. Exact duplicates of canonical action, provenance, and follow-up are suppressed. Proposal JSON files under `knowledge/assistant/plans/` remain regenerable projections of database state.

A Todo proposal references a Notion todo ID; a Goal proposal references a Goal or Subgoal ID and includes a short user-facing reason; an Opportunity proposal retains its originating opportunity title. Current names are resolved from the referenced source for display, with a generic label on lookup failure. A Goal question is an Assistant-authored backend message in the originating session and topic, not an approval record. Backend messages are included in later Assistant turn context even though they are not native Codex turns.

Pending function steps can be edited through the Assistant API/UI. The backend validates an edit against the live catalog and revalidates the final sequence at approval and immediately before execution. An approved `functions` action executes sequentially through `InvocationExecutor` with a named trusted backend context. It never creates an Act session or invokes Codex; execution stops on the first failure. The deterministic catalog excludes operations requiring a separate per-call approval. An approved `act` action creates one Act session and queues its instruction through the existing proposal path. Local and Telegram decisions use the same atomic claim. Pending proposals remain locally available when Telegram is disconnected.

Optional Goal or Opportunity follow-ups are persisted when approval is accepted. An absolute time is used directly; `after_calendar_step` is based on the approved Google Calendar creation step's returned event end plus the specified delay. The follow-up becomes sendable only after the action succeeds. Failure, cancellation, or interruption cancels it. When due, the backend inserts and sends an Assistant-authored message to the originating session/topic without Codex. A source session with a waiting or scheduled follow-up is retained so that its topic is not lost. Backend messages remain available in session history and are replayed as context to later Assistant turns.

## Assistant retention

At most five Assistant sessions are retained across web, Telegram, and assessments, ordered by creation time and ID. Before a sixth is created, the oldest is removed with its turns and activity, its credential is revoked, any foreign-keyed Telegram topic mapping is removed, and its Codex thread is archived. Archived Assistant sessions count toward the five. Busy oldest sessions and sessions with waiting or scheduled follow-ups block creation; they are never deleted while that work is pending. A SQLite write transaction serializes retention and creation across callers. Startup and completed turns reconcile excess records using the same rule.

Proposal records, approvals, knowledge, shared files, and linked Act executions survive session pruning. Source session IDs remain historical attribution. Codex rollout files are archived rather than physically purged.

Before each manual or scheduled assessment, the backend checks proposal references formatted as `todo:<Notion page ID>`, `goal:<Atlas goal ID>`, or `subgoal:<Atlas subgoal ID>`. If any attached item is missing, a Todo is done, or an Atlas Goal has 100% progress, it deletes the proposal record and its knowledge JSON. Linked Act sessions are preserved. Todo pagination must finish before absence is treated as deletion. Unavailable sources and legacy/unrecognized references are retained. Old Telegram approval buttons cannot approve a deleted proposal. This cleanup is permanent and applies to every proposal status.

## API

- `GET /agents`, `GET /agents/{agentId}`, `PUT /agents/{agentId}/policy`.
- `GET|POST /agents/{agentId}/sessions`, `GET|DELETE /agents/{agentId}/sessions/{sessionId}`.
- `POST /agents/{agentId}/sessions/{sessionId}/turns` and `POST .../turns/{turnId}/cancel`.
- `GET /agents/assistant/proposals`, `PATCH /agents/assistant/proposals/{id}/functions`, `POST /agents/assistant/proposals/{id}/approve|deny`.
- `GET|PUT /agents/assistant/assessment`, `POST /agents/assistant/assessment/run`.

The assessment service starts disabled. Enabling establishes a durable first occurrence 72 hours later. Each assessment uses a fresh Assistant session; failed/blocked claimed occurrences are consumed without retry. See [scheduling](scheduling.md) and [Telegram](../integrations/telegram.md).
