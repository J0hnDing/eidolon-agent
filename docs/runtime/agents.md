# Persistent agents

Act, Observer, and Assistant are built-in conversational agents backed by resumable Codex App Server threads. They are independent of generated function, service, and web-app skills and cannot be installed as skills. The Agents page owns Act and Observer conversations and exposes their configuration in a separate view. Assistant has its own home page with a permanent conversation, agenda, proposed actions, and settings. Skill-building Project conversations live under Skills → Build a skill. All three agents use the same conversation renderer; UI organization does not change backend authority.

## Workspace and authority

All three agents use `~/.eidolon/agents/` (`C:\Users\John\.eidolon\agents` on this installation), outside the source repository so repository development instructions are not inherited. Each agent's existing role instructions are supplied directly as its Codex base prompt on thread start and resume, replacing the built-in coding-agent prompt. The developer-instruction slot is explicitly empty so the role prompt is not duplicated. Managed processes and threads disable Codex global memory injection and generation; Eidolon owns their memory. Restart the backend to load these settings. New Act and Observer conversations avoid Codex instructions and memories retained in older histories; resuming does not rewrite historical messages. Shared workspace `AGENTS.md` contains the backend-maintained memory map, preserving unrelated user guidance. All agents receive `:root` read access; the native Windows elevated sandbox requires it when Codex loads `AGENTS.md`. They also receive read access to the managed `~/.eidolon/agents/` root. Act and Assistant can write workspace files and memory under their standing rules; Observer has no filesystem write grants. The backend owns synchronized knowledge and `knowledge/assistant/plans/`.

Named Codex permission profiles grant `:root` read, minimal reads, and the managed runtime root to all three agents, plus Act and Assistant memory/workspace write roots. Command networking is enabled for Act and Assistant. The backend disables inherited MCP servers except for Codex Security, the OpenAI Developers local-destination confirmation tool, and the read-only OpenAI Developer Docs MCP server at `https://developers.openai.com/mcp`, which are available to all agents; Playwright is available to Act and Assistant. The local-destination confirmation exception permits only `confirm_openai_api_key_local_destination`; the backend rejects any additional tools on that MCP server. This confirmation tool asks for a workspace-local env-file destination and cannot read or write a key. The Developer Docs server is restricted to the exact official endpoint and provides read-only documentation search and page content. Remote plugin catalog loading is disabled per managed process because a stale Cloudflare plugin entry fails configuration loading before named-server disables apply. Other plugins, apps, and delegation features remain disabled for every managed agent process. Codex Security and the local-destination confirmation server are temporary allowlist exceptions while Codex ignores per-process plugin disable overrides. An unsupported permission profile fails the turn instead of falling back to a broader sandbox. Filesystem read, filesystem write, network, and tool availability are separate controls. These are local single-user boundaries, not protection against a privileged host user or compromised backend.

Each agent has a default semantic read-only filter, maximum risk, explicit allowed function IDs, and explicit banned IDs. Bans win; explicit allows override the default semantic filter and risk limit. Integration read-only decisions use canonical registry effects, never MCP presentation hints. Ordinary catalog operations retain their availability, integration authorization, generated-function runtime permission, and per-invocation approval rules. Observer defaults to read-only operations at any risk; Act and Assistant default to write-capable operations; generated functions remain write-capable by default. Act permits all available agent-callable functions. Observer has no web search; Act and Assistant have live Codex search. Filesystem and search permissions are fixed per role in this milestone; editable function overrides do not change them.

## Authenticated MCP and durable turns

The public host MCP registration remains separate. Managed threads start with a required private STDIO MCP registration and an opaque credential bound to the agent and Eidolon session. Only credential hashes are stored in the application database. The credential is passed to the trusted MCP child, not ordinary shell processes or readable workspace files. Discovery filters the catalog and every invocation rechecks current identity and policy. Audit records include agent/session identity and the active turn when established, without arguments or credentials. Deferred function approvals retain agent attribution and recheck current policy at dispatch.

Sessions are saved before Codex starts; their first queued turn creates the Codex thread. Act runs one managed App Server process and sequential worker per session, allowing different Act sessions to execute concurrently. Observer retains its serial dispatcher and managed process. Assistant has a dedicated daily dispatcher, one permanent chat, and one live daily Codex thread; see [Primary Assistant](assistant.md). Telegram and WeCom are transport-only adapters over this same session infrastructure: Act/Observer Telegram resolves `(chat_id, message_thread_id)`, Assistant Telegram uses its paired direct private chat and WeCom resolves one persisted current session per user. A connected Act/Observer Telegram bot projects every newly committed active non-WeCom session for its agent to an idempotent topic mapping; pairing, polling, and status refresh backfill or retry missing projections. Each paired WeCom user always has one active current Observer session: pairing creates it, clear swaps it, and archiving it through Chat atomically replaces it for the same user. Turn rows snapshot the delivery provider, connection, chat/user, and Telegram thread so channel changes cannot redirect replies. Model routing is also independent: Act uses `act`, Observer uses `observer`, and Assistant uses `assessment` in the persisted Codex routing settings. All three agents return nullable `title` metadata alongside their normal answer in the same structured response, including background Assistant reviews. The ordinary Evening reflection agenda task is instructed to save its summary through a private memory tool and return an empty final response; the backend does not rewrite its final answer as a summary. Backend session metadata requests a concise title only while the session is unnamed (`New Chat` or empty); later responses return `null`. After a successful turn, the shared title-sync service explicitly sets a missing native Codex thread name through `thread/name/set`, then projects it to the session and existing Telegram topic. App Server does not supply an automatic title-generation guarantee, and the setter is a metadata request rather than an additional model turn. Existing native names and manual session/Telegram names take precedence over generated suggestions; a missing native name is restored from an existing local title. Existing unnamed sessions are titled on their next successful turn. Telegram manual renames update the native thread name. The shared title-sync service compares normalized values and keeps Telegram transport failures separate from turn success. Title synchronization finishes before the turn receives its terminal success status, so the Chat UI's final poll sees the new title; failed naming can retry on a later turn. Act and Observer App Server processes restart at turn boundaries to refresh tool discovery and configuration. Assistant retains its live process between successful turns and starts a fresh thread at local 04:00 when idle, with startup recovery for a missed boundary or after an explicit refresh request. The new Assistant thread receives current persistent state without prior chat transcripts. Act browser ownership is independent: one backend-owned persistent browser shares website authentication across conversations, while each conversation retains its own tabs and selected page across turns. Agent restarts and per-turn credential revocation do not close these pages; archive closes only the selected conversation's pages, and backend shutdown closes the shared browser. Act and Assistant receive the private `browser.authenticate`, `telegram.send_file`, and `chat.send_message` runtime tools, while Playwright remains a managed action-agent tool surface through the trusted shared-browser proxy. These invocation surfaces are absent from Observer, public MCP, the function catalog, and generated skills. Act/Observer credentials are revoked after turns and archiving. Assistant retains its session-bound credentials through successful daily turns and revokes them on refresh, failure/cancellation or shutdown. Existing Act session/thread IDs are preserved, and the `/act` API remains an Act-only surface. Cancellation, archive, restart interruption, and missing-rollout recovery retain Act's existing behavior.

## Completed chat storage

For all three agents, `memory/chat-history/` is the only completed-message content store. The backend archives complete messages durably and erases terminal turn/live text from SQLite, preserving runtime IDs and receipts. Session API responses project retained files into detached response models; display reads never restore text into ORM entities. The same files supply pending delivery, missing-rollout recovery and Assistant execution review. When retention deletes a message, those paths cannot recover it from SQLite or browser storage. The permanent Assistant chat retains its identity, with only retained messages visible. Retention runs every minute and at startup/access even when proactive Assistant is disabled. See [Primary Assistant](assistant.md) for bounds and migration.

Archive scans refresh database rows even when a polling request already loaded them. The terminal cleanup scan refreshes again and archives newly completed pending turns before erasing SQL text, including during the first migration pass. This preserves replies when a dispatcher finishes while a history synchronization is in progress.

## Primary Assistant

Assistant owns a durable agenda of tasks and questions, including ordinary recurring Morning planning and Evening reflection tasks, and a primary natural conversation. It shares Act's runtime capabilities and uses explicit autonomy rules to judge when to act or ask. See [Primary Assistant](assistant.md) for state, tools, activation, learning, recovery and migration contracts.

## API

- GET /agents, GET /agents/{agentId}, PUT /agents/{agentId}/policy.
- GET/POST /agents/{agentId}/sessions, GET/DELETE /agents/{agentId}/sessions/{sessionId}.
- POST /agents/{agentId}/sessions/{sessionId}/turns and POST .../turns/{turnId}/cancel.
- GET /agents/assistant/proposals, PATCH /agents/assistant/proposals/{id}/functions, POST /agents/assistant/proposals/{id}/approve|deny.
- GET/PUT /agents/assistant/runtime (proactive enabled/timezone), POST /agents/assistant/runtime/refresh.
- GET/POST /agents/assistant/agenda, PATCH/DELETE /agents/assistant/agenda/{id}. Task recurrence uses the same activation path as the rest of the agenda.
- POST /agents/assistant/agenda/{id}/run with expected_revision; GET /agents/assistant/agenda/{id}/occurrences (up to 100, newest first).
