# Frontend UI

The frontend is a React/Vite TypeScript app under `frontend/src`. Its local development server uses the fixed origin `http://localhost:5174`, keeping it distinct from the separate Eidolon marketing site.

## Navigation

Routes are defined in `frontend/src/App.tsx`:

- `/assistant` (default home)
- `/assistant/details` (agenda, questions, actions, and Assistant settings)
- `/agents`, `/agents/act`, `/agents/observer`
- `/memory`
- `/skills`
- `/skills/build`
- `/apps`
- `/apps/:skillId`
- `/skills/:skillId`
- `/automations`
- `/activity/approvals`
- `/activity/runs`
- `/activity/runs/:agentRunId`
- `/settings/appearance`
- `/settings/usage`
- `/settings/project`
- `/settings/models`
- `/settings/integrations`
- `/settings/integrations/:integrationId`
- `/settings/permissions`
- `/settings/functions`

The compact sidebar begins with Assistant, Agents, and Memory, followed by Applications, Skills, Automations, and Activity under Workspace. Settings is anchored at its foot. The brand row contains the Eidolon symbol, name, and search control. There is no account/workspace footer, local-workspace indicator, or brand tagline. Assistant owns the permanent conversation; Agents owns Act and Observer sessions; Skills → Build a skill owns Project conversations. Activity combines permission approvals, invocation approvals, Assistant proposals, and build/repair execution history. Its badge counts pending requests from all three approval sources, updates after decisions, and refreshes periodically.

The Go to… page switcher opens from the search icon beside Eidolon or Ctrl/Cmd+K. It searches navigation destinations and settings, supports arrow keys and Enter, closes with Escape, and restores focus. It does not search personal records or invoke work. Each page uses its own concise title in the content pane; there is no duplicate global breadcrumb bar.

Desktop navigation remains visible. Narrow screens use a labelled menu button and a dismissible drawer with Escape handling, focus containment, and focus restoration. Closed mobile navigation is inert; the page is inert while the drawer is open. Active destinations remain visibly selected and a skip link targets the main content. Secondary routes load on demand with a visible loading state.

Legacy `/chat` follows the previously selected conversation to its new home, preserving session links and stored build history. `/act` opens Agents → Act; `/agents/assistant` opens Assistant; `/schedules`, `/functions`, `/agent-runs`, `/agent-runs/:id`, and `/approval-requests` redirect to their canonical Automations, Settings, or Activity locations. Unknown routes provide a return to Assistant.

## Visual and Interaction System

The visual system follows the user's supplied Linear application screenshot. It supersedes the marketing-canvas proportions in `Tools/awesome-design-md/design-md/linear.app/DESIGN.md`: a `#111214` sidebar frames an inset `#191a1c` charcoal content pane with a thin border and rounded outer corners. Lifted neutral surfaces, muted text, compact navigation, and restrained lavender actions establish hierarchy. Inter is bundled locally with its license; IBM Plex Mono is reserved for code. A neutral light theme preserves the same hierarchy. The Eidolon mark is a simple monochrome symbol made from two interlocking loops, with no letter or colored background tile. It is used in navigation, conversation authors, welcome views, and the favicon.

Shared controls use 6–8px corners, panels use 8–12px corners, and a 4px spacing scale supports readable content. `styles.css` owns tokens and primitives; `product-shell.css` owns the reference-based product frame, compact sidebar, page-title rows, and toolbar proportions. `conversations.css`, `catalog.css`, `records.css`, `settings.css`, and `skill-detail.css` own their respective surfaces. The content pane scrolls independently of the sidebar. Conversation layouts keep their transcript and composer within the available pane height.

Page headers show a concise title and relevant actions. Promotional introductions, repeated workspace labels, welcome taglines, and composer footers are omitted. Functional explanations remain next to the setting, permission, field, or empty state they explain. Agents uses one compact agent selector and view toolbar rather than introductory cards and a repeated agent heading. Catalog runtime filters use compact pill controls.

Passive status presentation uses a small semantic dot with a plain-text label instead of a colored capsule. Color is never the only state signal. Skills, functions, and schedules with an active execution replace their normal state with a tooltip-labelled lavender dot and the `running` label in the row's state column; its glow pulses without moving the row content. Hover effects are short and quiet. `prefers-reduced-motion` disables non-essential animation, and focused controls retain an explicit visible ring.

Delete actions generally use a consistent square red trash-icon button. Each icon-only control retains a specific accessible name and matching hover tooltip that identifies the record being deleted. Skill Detail instead uses an explicit **Delete Skill** text button in its title bar. Like Chat's Send control, destructive buttons switch to a solid semantic background and contrasting text or icon color on hover.

Settings has grouped secondary navigation beside a focused reading column and uses horizontal section navigation on narrow screens. Conversation surfaces follow a ChatGPT-style transcript: a bounded reading width, spacious assistant replies, quiet user bubbles, searchable history, and a composer anchored below the independently scrolling transcript. Welcome suggestions populate a draft and never submit a task automatically. Approval Requests uses a filtered inbox with a selectable request list beside a readable detail panel.

## API Client

WhatsApp appears under Messaging in Integrations. Its focused Settings panel
handles QR pairing, connection and available-history status, reconnect, cache
clearing, and disconnect. Cache clearing and disconnect use Eidolon modal
confirmations. QR codes are fetched only by the mounted pairing panel; the
integration overview never receives them. See [WhatsApp](../integrations/whatsapp.md).

`frontend/src/api/client.ts` defines API types and request helpers. Frontend types mirror backend schemas for skills, runs, versions, approvals, schedules, generation requests, and agent runs.

Concurrent identical GETs share one in-flight request. This prevents React development-mode mount replays and overlapping page consumers from duplicating read-only backend work; completed responses are not cached, so later navigation and explicit refreshes still read current state.

## Conversation Surfaces

`ChatPage` and `ChatWorkspace` provide one conversation implementation, embedded in the destination responsible for that conversation. The destination restricts creation and selection to its own mode, without changing stored modes, IDs, backend session bindings, or approval workflows:

- `project`: writes the initial message unchanged through the one-time intent placeholder, then starts a resumable `pm_plan_build` session for a reusable skill request. The placeholder does not call Codex. The session may ask a clarification question or reject the request before any blueprint, permission, or task DAG artifacts are created; the next reply in the same chat resumes the same generation request and Codex thread.
- `act`: binds the local conversation to a backend-owned durable Act session and renders its queued/running/terminal turns in the shared transcript.
- `observer`: uses the same shared transcript for durable Observer sessions, including externally started conversations.
- `assistant`: reuses the backend primary Assistant session automatically and exposes no session list or new-conversation control.

Conversation mode is fixed after creation. Fresh storage starts in Assistant; an unbound initial Assistant conversation attaches to the primary active session while preserving its draft. Agents has Act/Observer navigation and Conversation/Configuration views; changing configuration views preserves the mounted conversation. Configuration uses one stable scroll area beneath the agent toolbar. Policy & model and Effective functions are separate local views; both remain mounted so policy drafts and function filters survive switching between them. Policy groups function defaults, explicit overrides, and model settings, while Effective functions provides searchable allowed/blocked visibility. Its **New conversation** action creates only the selected agent's session. Build a skill has a separate saved-build list and **New build** action. Both conversation lists support title search. Each home remembers its own selected conversation. The transcript header shows mode and conversation title, with creation time and any WeCom owner displayed directly. There is no in-conversation mode switch. Unsupported legacy direct-chat records are discarded, without converting them into skill requests.

Desktop conversations fill the available viewport with independently scrolling history and a visible composer. Agents and Build measure remaining space through grid rows, including wrapped headers. Narrow screens stack the conversation selector and transcript. Archiving an agent conversation and deleting a build conversation use Eidolon confirmation dialogs. The permanent Assistant chat has no delete control. Managed drafts survive navigation in browser memory without being persisted to local storage.

Replies render Markdown with lists, links, code, and tables. Raw HTML and executable URLs are excluded; remote images are explicit links instead of automatic network fetches. User messages remain plain text. The composer accepts multiline input, Enter sends, and Shift+Enter inserts a line break. Transcript scrolling follows new messages only while the reader is near the bottom. Per-conversation request revisions prevent older overlapping session reads from overwriting newer messages or live-reply state. An unaccepted failed send restores the draft; recovery checks whether the backend actually accepted the new turn before clearing the error.

Transcript messages have no horizontal rules. A quiet centered date/time marker appears before the first timestamped message, after a gap of at least three hours since the preceding timestamped message, or when the browser-local calendar date changes. Consecutive turns have no individual timestamps. Managed conversations use backend request, live-message, and completion times; new Project messages retain their local creation times. Legacy messages without timestamps remain readable without inventing historical dates; transient thinking placeholders do not create markers. A fresh Project opens with “Hi, what can I build for you today?” and a fresh Act opens with “Hi, what can I do for you?” Welcome views include contextual draft suggestions. New Act creates its local conversation immediately and attaches the backend session without reusing message-send loading UI. Active Project and Act turns share one visible “Eidolon is thinking…” treatment; Act does not add a second polling placeholder. Each Act response includes a collapsed work-details row with live elapsed time while queued or running, persisted elapsed time after completion, and concise backend-recorded activity, including the tool name when Codex returns it. Raw model reasoning is not fetched, reconstructed, or displayed. User messages use a conventional right-aligned text bubble. Eidolon responses use the readable transcript width and visible role label **Eidolon**, never **assistant**. The composer uses an upward-arrow Send control with an accessible text label. Enter sends and Shift+Enter adds a line break.

Managed conversations keep up to 20 recently refreshed sessions in a shared browser-memory cache, keyed by agent and backend session. Returning to a loaded chat renders its cached transcript and active-turn state immediately while session discovery and transcript refresh run in the background. The first uncached visit shows a neutral loading state while discovering sessions and fetching the selected transcript. The welcome screen appears only once the selected conversation is confirmed empty. A failed initial history read offers Retry conversation without showing the welcome screen; subsequent polling preserves an already loaded transcript. Sending waits for initial history to load, while draft editing remains available.

Agent conversations bind to existing backend sessions, including sessions started through Telegram, WeCom, or background Assistant activations. Modes use explicit text and distinct glyphs within the shared neutral/lavender system. Opening Assistant selects the primary active session automatically; its first message creates the primary session when none exists. Agent deep links accept `?session=<id>`. Project creation is reachable only through the explicit Build a skill surface.

Build-time and runtime approvals are rendered inline in the chat transcript. Approval messages must remain in chat history when the user navigates away and returns. Project chat synchronizes its conversation-scoped generation request, linked agent run, proposed skill, and latest build/runtime approvals from the backend, so a response lost after a committed request or a decision made on the global Approval Requests page is recovered inline without duplicating messages.

Medium/high-risk caller-to-function relationships use normal Approval Requests entries with caller name, target function, description, derived risk, and explicit approval boundaries. Low-risk declared relationships are summarized during runtime review and do not create redundant approval rows.

Project chat persistence uses local frontend storage managed by `frontend/src/lib/chatStore.ts`. Managed Assistant, Act and Observer chats persist only session/selection metadata there, with no message, live-message, activity or draft content. Legacy managed transcripts are scrubbed from local storage on read. Their completed messages come from the backend file archive and remain in browser memory across page navigation, without storage persistence. A full page reload clears the cache; background refresh replaces cached content with the current backend transcript. Archiving or reconciling a removed session evicts its cached history. Every transcript is owned strictly by its conversation id: a temporarily unavailable selection renders a clean Assistant placeholder rather than falling back to another conversation, and the transcript subtree remounts when the selected id changes. Project conversations also store the pending generation request id while ProductManager is waiting for clarification so the user's next reply stays attached to the same request. Agent conversation titles remain `New Chat` until `ChatPage` receives the persisted `ActSession.title`; polling and session-list imports update both the transcript and sidebar from that backend value.
Users can delete Project, Act, Observer, or Assistant conversations from the conversation toolbar. Project deletion removes the local transcript and asks the backend to remove persisted message rows for the same frontend conversation id; Project-mode approval records remain available through the approval pages. Agent conversation deletion archives the shared backend session before removing the local transcript. Deleting a WeCom-owned Observer session creates, imports, and selects the fresh current session for the same WeCom user.

Approving a Project build-time request from either its inline chat card or the global Approval Requests page continues the linked agent run automatically. A separate Agent Run resume click is reserved for quota pauses, recoverable workflow failures, or explicit user-action blockers rather than ordinary permission approval.

`ChatPage` retains route-level API orchestration, imports active backend Act, Observer, and Assistant sessions, reconciles archived or pruned bindings, and polls the selected agent conversation while its turn is queued or running. An open Assistant conversation also polls while idle so proactive messages appear without a reload. Deleting an agent conversation archives its backend session first; active work can be cancelled from the shared composer. `features/chat/useChatConversations.ts` owns local conversation selection, creation, deletion, drafts, fixed modes, agent-session bindings, and message transitions; it persists the synthesized first conversation before accepting edits. `features/chat/ChatWorkspace.tsx` owns the sidebar, fixed mode display, transcript, approval cards, and composer presentation.

## Skills Page

Skill, function, application, and schedule names are displayed from their canonical names by replacing underscores with spaces and capitalizing each word. Manifests do not carry a separate UI display name.

Skills uses a searchable catalog with All skills, Functions, Applications, and Services runtime filters, a combined availability filter, result counts, and clear empty/filter-reset states. Spacious desktop rows become labeled record cards on phones. A row replaces its normal Status value with the `running` indicator while its bounded runtime executes or while its persistent web application instance is active. Each row opens Skill Detail, including web application rows; application launch remains on the Applications and Skill Detail pages. Quiet row arrows appear on hover or keyboard focus. Services show the same backend-owned enabled/disabled availability as other skills. User-facing creation goes through the proposed-skill workflow, not bare database record creation.

## Functions Page

`/settings/functions` displays the backend-owned unified catalog. It includes backend-core, installed user, and integration functions in every state, with id, description, source, risk, version, availability, unavailability reasons, and the `running` indicator replacing the Availability value when a persisted function run or audit is active. Integration sources use the specific provider name, such as GitHub, Google Calendar, or Gmail, while the underlying catalog category remains `integration`. The page supports combined keyword, source, availability, and risk filters, polls the catalog so enablement, deletion, dependency changes, integration connection changes, and running state remain visible, and its Refresh action explicitly rebuilds the catalog projection. Only available entries are injected into ProductManager prompts.

## Primary Assistant

`/assistant` is Eidolon's default home, focused on the permanent conversation. **Assistant details** opens `/assistant/details`, a dedicated page within Assistant for agenda tasks and questions, proposed actions, current work, runtime status, and settings. Section links select one focused view: Agenda & questions, Actions, Settings, or Tool access. The selected view is encoded in `?view=` for direct links and browser history. Visited sections retain their drafts and filters while hidden. Runtime settings include proactive enablement, timezone, and session refresh; Tool access contains function policy, model settings, and effective functions. Actions use searchable rows filtered by awaiting review, in progress, or all; a row opens a dedicated review dialog before any approval confirmation. Agenda and Questions use full-width lists with title/context search, current/past navigation, status filters, and schedule or question-category filters. Each row opens a detail dialog with complete notes, timing, recurrence history, and explicit actions. Creation and editing use focused Eidolon dialogs; consequential action approval still requires its confirmation dialog. Opening the conversation reuses the primary active session or the latest active session; a first message can create the primary session directly. There is no session picker, five-session retention notice, or assessment workflow.

The Assistant agenda has Tasks and Questions filters plus Current and Past views. Current shows open and waiting items; Past shows completed and dismissed one-time items and recurring tasks with occurrence records. Past recurring tasks can load their most recent 100 occurrence records on demand. Items remain editable and closed items can be reopened. The Questions tab shows today's descriptive asked count, the configured timezone, and each question's scheduled ask time. The Assistant plans questions through the ordinary agenda; asked questions wait for an answer. Questions store meaningful uncertainty and its context. Edits and deletion use the item's revision to avoid overwriting concurrent Assistant changes. Conflicts preserve the user's editor draft. Deletion uses an Eidolon-rendered confirmation. Next-check inputs show the browser's timezone and convert local dates to explicit UTC instants; invalid local times are rejected.

Question cards and editors distinguish Common, Important and Temporal questions. Questions use the ordinary next-check time; important/temporal questions without a time are due immediately. The daily asked count is descriptive, with no quota or fixed daily question slots.

Tasks can repeat daily, weekly on selected weekdays, or monthly on a selected day at a local time in an IANA timezone. Monthly schedules skip months without the selected day. Some Assistant-managed tasks display an outcome requirement, such as requiring an interaction today or producing scheduled agenda work; editing the task preserves that requirement. Recurring cards show their schedule, next occurrence and latest occurrence status; failed attempts also show a retry time. Run now, Pause schedule, Resume schedule and End recurring task use the item's current revision. Waiting pauses recurrence, while Done or Dismissed stops it. Questions remain one-time agenda items. The editor explains that only the latest missed occurrence is recovered after downtime.

Morning planning and Evening reflection appear as ordinary editable recurring tasks in the agenda, with the same schedule editor and actions as any other recurring task. Assistant settings contains proactive enablement and the Assistant timezone for session refresh and question attention context; it has no dedicated review/summary times or run actions. Task timezone is configured on that task. Background polling refreshes agenda, proposals and runtime state without replacing unsaved settings or item drafts. Concrete consequential action proposals retain the existing inspect/edit/approve/deny controls.

Chat and Agents omit internal activation prompts and quiet background turns. Useful answers, live notices/replies, and failures remain visible, with execution activity collapsed. Assistant supports the same expiring live-reply flow as Act, including interactive authentication notices. An open Assistant chat continues polling at a slower interval while idle so useful proactive messages appear naturally.

The Memory page uses a collection rail for Overview, Agenda, Questions, Daily summaries, Facts outside Atlas, and Chat history. The overview shows active task/question counts and previews, saved fact and summary counts, and a recent summary journal. Facts use compact rows with title/value/evidence search and a source-attribution filter. Opening a row shows the complete fact, evidence, and timestamps in a detail dialog, with explicit edit/delete actions; failed saves preserve the draft. Fact deletion uses a confirmation dialog. Agenda and Questions reuse the Assistant editor and its existing backend records, including Current/Past views, revision checks, question categories, scheduled times, completed/dismissed items, recurring occurrence history, and deletion confirmation. Answers and evidence remain visible in item notes. No duplicate agenda store is created.

Daily summaries use concise dated rows, newest first, with pagination, text search, and a month filter. Search loads the saved summary pages on demand and filters the complete collection rather than only the displayed page. Opening a summary shows its complete text and source file in a detail dialog; overview summaries open the same reader. Chat history browses the retained Assistant, Act, and Observer archive by UTC date and optional agent, with paginated full messages and local display timestamps. A clearly labeled search filters messages on the current page; it does not imply archive-wide search. Older conversation dates remain reachable through Load older dates. Archive browsing reads existing files without migrating or reconstructing pruned messages. Retention remains 30 days or 50 MiB across all agents. Refresh reloads the current memory data; source-specific failures are visible and retryable without blocking the other sections.

Facts outside Atlas retain generic create/edit/delete controls and provenance/evidence in their detail dialog without imposing a preference/category ontology. A collapsed storage disclosure shows the configured memory root and the `memory/facts-outside-atlas/`, `memory/daily-summaries/`, and `memory/chat-history/{assistant,act,observer}/` layout. Atlas records remain in Atlas; the existing Open agent workspace action provides access to the editable files.

## Automations Page

The catalog combines keyword, automation-type, and active/paused filters with result counts and recoverable empty states. Desktop tables become labeled cards on phones, keeping schedule state, recurrence, next/last run, and action controls visible together. Last-run status dots keep a 12px gap from their timestamps in both layouts. Editing uses the shared focus-contained modal; advanced JSON stays collapsed until requested.

The top-level Automations page at `/automations` is the schedule management surface for generated and backend-owned services. The table uses fixed column allocations so status, timestamp, and action changes do not shift the column boundaries; narrower viewports scroll the table instead of redistributing it. The Service column shows the service name and links generated services to Skill Detail; those links use the same hidden blue reveal arrow as Skills rows, while non-navigable platform schedules show no arrow. The Status column shows `active` or `paused`, replacing that value with the `running` indicator while the generated or platform schedule is executing. The Schedule column contains only the human-readable recurrence. Recurrence and next/last timestamps omit timezone names and abbreviations from the table; the Edit modal retains the timezone field that controls execution. Every service row supports edit, enable/disable, and Run Now. Generated and ordinary platform Run Now actions are available only while enabled. Assistant Morning planning, Evening reflection and other recurring tasks are managed in the Assistant agenda rather than represented as service schedule rows. Actions are left-aligned, Enable and Disable share one stable width, and ordinary Edit actions open the existing schedule form in a modal. There are no create, delete, or schedule-approval controls because every service owns exactly one required schedule. Last Run places a status-colored dot before the timestamp and exposes the status text from the dot's hover tooltip instead of repeating it inline. Schedule rows keep one consistent desktop height, including rows with action buttons. New backend registry services inherit the action set automatically.

The Codex Model panel is available on every Skill Detail page. Skill Detail uses a compact title bar with a square back control on the left and the **Delete Skill** action on the right. Versions lead with the version list, show validation and test outcomes as labelled status dots, and place the improvement/repair controls beneath the list. An approved runtime contract uses the success status color and exposes no redundant review action. Files uses a searchable file navigator beside a bounded source reader. Navigation actions within Skill Detail use buttons instead of standalone blue text links.

## Applications Pages

Applications uses searchable launch cards with a combined availability filter. Each card separates application launch from skill inspection. The embedded application page retains trusted host controls and a return to Applications above the isolated frame; containment explanations and lifecycle diagnostics open in a focused dialog without remounting the application frame.

`ApplicationsPage` lists only `runtime = web_app` skills. Function skills do not appear there and have no separate interface page in the current milestone. Each application card links separately to Open Application and Open Skill Details. Installed enabled web applications open through `/apps/:skillId`; the opened application chrome does not repeat the Skill Detail control.

`WebAppPage` asks the backend for a ready, version-pinned application session and keeps trusted identity, version, lifecycle status, containment disclosures, stop control, logs, and bounded audit status outside the frame. It embeds only an HTTP(S) hostname under the configured `*.web-app.localhost` gateway domain; ordinary external or credential-bearing URLs are rejected. The iframe uses `sandbox="allow-scripts allow-forms allow-same-origin allow-modals"`, an empty browser-feature allowlist, and `no-referrer`. The page coalesces Strict Mode mount replays into one session-open request. The backend supplies the complementary CSP and Permissions Policy. The page polls diagnostics while the application is healthy and displays readiness/failure details without trusting application-rendered status.

If the backend gateway domain is customized, `VITE_WEB_APP_GATEWAY_DOMAIN` must match it. The application runtime and containment contract is documented in [Sandboxed web applications](../runtime/web_applications.md).

## Agent Runs Pages

Activity presents Approvals as an inbox with Permission approvals, Invocation approvals, and Assistant proposals tabs. Search combines with Needs review, All requests, and History. The selected detail always belongs to the visible filtered list, and approval applies to that displayed record. Human-readable explanations and access scopes lead; raw payloads remain available under Technical details. Loading and initial failures never claim that the inbox is clear. Executions has request/status filtering, readable workflow rows, and a detail page with Workflow, Build artifacts, and Skill Run History views. Deletion requires an Eidolon confirmation.

Agent Runs list and detail pages show run status, current task node or parallel active nodes, current step, step logs, DAG progress, node failures, and applicable retry/cancel controls. ProductManager, Builder, and Tester steps expose the exact complete prompt sent to Codex—including instructions and composed inputs—and the exact final response returned by Codex. Backend-only permission, dependency, validation, finalization, and bounded-stop steps are labeled `Backend` and show only a fixed summary, never agent input/output controls. Historical agent steps without a recoverable exact transcript are labeled unavailable instead of falling back to normalized workflow JSON. Task-DAG failures expose run-level and failed-step retry actions. Single-Codex errors are terminal and expose no retry action; only a pre-invocation quota pause may resume. Cancelling an active Codex-backed run terminates its owned Codex process and leaves the run cancelled; it cannot later become failed or create runtime approvals. Workflow steps are searchable and status-filtered rows. A step opens a dialog with Log, Agent input, Agent output, and Codex invocations views; backend steps omit the agent transcript controls. Build artifacts selects one recorded artifact at a time, including the task DAG using each stable node id, task prompt, status, dependencies, write paths, assigned function ids, per-node Codex tokens, build totals, usage pause reason, and resume control. Skill Run History uses the shared searchable list and detail dialog for the linked skill with separate runtime Codex totals and per-invocation success/failure metadata, including retained CLI diagnostics for failed calls. Skill detail shows completed agent-run token totals.

## Codex Settings

Settings uses a grouped secondary sidebar and focused reading column so each concern has a focused URL and loads only the data it needs. General contains Appearance and Usage & CLI; Intelligence contains Model routing and Project builds; Connections & tools contains Integrations, Functions, and Permissions. `/settings` redirects to `/settings/appearance`.

`/settings/appearance` lets the user choose Dark or Light. The choice is stored in local browser storage and applied immediately to the document. Dark is the default when no choice has been saved.

`/settings/usage` shows the resolved CLI and both the 5-hour and weekly Codex allowance windows. DAG builds pause before the next ready batch when either window has less than 5% remaining. Refresh reads current local App Server state; it does not infer quota from project-build token totals. Skill runtime calls remain excluded from build token accounting.

`/settings/project` presents explanatory radio cards to keep automatic Project build workflow selection or force every new build through Simple (`single_codex`) or Task DAG (`task_dag`); forced selection overrides ProductManager output in the backend.

`/settings/models` labels the existing blueprint route **Project planning and clarification**. It loads the live App Server model catalog and lets the user choose model and reasoning effort independently under **Agent Routing** for Act, Observer, and Assistant, with separate local views for ProductManager actions, the single-Codex Builder and Builder difficulty tiers plus repair/update, and Tester task/final/update actions. Switching views preserves unsaved routing choices. A sticky **Save model routing** bar shows whether changes are unsaved or when the persisted routes were last saved. Unsupported model/effort combinations are rejected by the backend.

`/settings/integrations` is a searchable directory grouped into Connected apps, Messaging, and Local tools & data. Keyword and connection-state filters combine, with a result count and resettable empty state. Each integration has a named, keyboard-accessible card with a locally stored brand mark or interface icon, a short description, a connection-state dot and text, and a trailing arrow. Provider cards form two columns on desktop and one on phones. The overview loads sanitized status metadata and never renders credential forms. Refresh checks all overview statuses; detail pages still load only their selected provider and retain a return to the directory.

Brand marks retain their colors in both themes: Google uses its multicolor G, Telegram its blue mark, WhatsApp its green symbol, and WeCom the official Tencent logo. ## Targeted Polling

The MVP uses targeted polling, not push events. Pages with changing backend state poll only relevant resources and should stop or slow down once records reach terminal states.

Act live messages and replies appear in chronological order inside their parent turn before the thinking or final response. When `chat.send_message` is waiting for a reply, Assistant and the Agents conversation surface enable one reply submission while retaining cancellation. The waiting deadline closes the composer locally even if polling fails; the backend atomically accepts only the next reply and returns it to the same running capability call. Ordinary busy-session sends remain disabled.

Assistant uses one permanent chat. The runtime settings include **Refresh Assistant session** and a pending indicator; refresh takes effect as soon as idle and keeps visible history while starting a fresh Codex thread without chat transcript injection. The chat also accepts `/refresh`.

Assistant runtime displays the fixed daily 4:00 AM session refresh and the next boundary in the configured timezone. Startup recovers a missed boundary once before model work; visible history stays in the permanent chat.
